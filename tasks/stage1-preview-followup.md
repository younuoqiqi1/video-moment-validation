# AGY 任务：阶段 1 镜头清单核对补充

## 目的与范围

这是阶段 1“素材导入与时间码清单”的小范围 POC 补充，用来确认真实视频生成的 130 条时间码清单是否可查看、统计是否一致，以及长镜头是否有明显漏切。

只处理阶段 1。本任务不做口播稿拆分、语义镜头检索、成片或阶段 2，也不要求每个镜头固定为 3 秒。切分规则应根据真实画面核对，不得为了让镜头数量变多而盲目降低阈值。

## 已发现的问题

- Mac 上的 `outputs/stage1/summary.html` 只显示前 100 条，剩余 30 条只能去 JSON 查看。
- 用户在网页前 100 条中看到一个约 **210.90 秒**的区间。
- PR 和 `reports/stage1-media-import.md` 写的最长时长为 **58.88 秒**。
- 因此当前网页、报告和用户所见数据尚未对齐，不能直接把镜头切分质量标成已验证。

## 执行步骤

1. 在 Mac 上拉取当前 PR 分支最新提交，先确认 Git 工作区和本地素材状态；不覆盖用户改动。
2. 以本次真实运行生成的完整 `scenes_*.json` 为数据源，核对总条数是否为 130，重新计算平均、最短、最长时长。检查每条的起止时间码、帧区间和时长是否相互一致，相邻区间是否连续。
3. 让 HTML 能查看完整 130 条，而不是静默只显示前 100 条。给每条增加轻量画面预览（例如该段起始帧缩略图或一张联系表），以便用户快速判断清单内容。原片、帧图及其他媒体产物只留在本机 Git 忽略目录，不上传、不提交 Git。
4. 重点核对约 210.90 秒的长区间以及完整 JSON 中最长的区间：查看区间起点、内部代表位置和终点附近画面，判断是否存在明显的镜头变化漏检。若发现漏检，基于实际画面调整规则并重跑前 30 分钟；如果没有漏检，也记录为何长区间合理。不要把“固定 3 秒”作为切分标准。
5. 从同一份完整 JSON 更新 HTML 和 `reports/stage1-media-import.md` 的统计，保证数据一致。若最新数据与 210.90 秒或 58.88 秒不同，说明使用的输入/运行版本及原因，不要只改文案迎合某个数字。
6. 补最小测试：HTML 展示完整清单（包含第 101 和第 130 条），摘要统计基于完整清单；合成短片测试只能证明程序逻辑，不能写成真实素材切分质量已通过。
7. 报告用简单中文列出实际运行命令、完整统计、核对过的区间与观察结果、测试结果，并分开标记“程序测试”和“真实视频人工抽查”。完成后更新本 PR，保持 PR 打开并停在 awaiting_review。

## 进度通知与阶段门禁

开始实际编码后，在 PR 评论中说明已开始及正在处理的项目；完成后推送真实代码提交，等待 Codex 复核。不要只发“已开始”而不提供代码进展。不要合并 PR，不要开始下一阶段。
