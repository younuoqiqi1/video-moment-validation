## 必须修正

### R2a-1（P2）：JSON 发布失败后仍留下“全部通过”的 HTML

位置：`src/vmv/report.py` 的 `write_status_reports` / `run_status_stage`。

当前顺序是先 `os.replace` 发布 HTML，再发布 JSON。若第一次成功、第二次因权限或文件系统异常失败，程序返回失败且 JSON 不存在/失败，但已经发布的 HTML 仍显示“通过 (All Passed)”。这会让人工打开网页时误以为环境检查成功，违反 R2“避免留存误导性成功结果”。

独立复现：模拟工具检查全部通过，只让 JSON 目标的 `os.replace` 抛出 `PermissionError`。结果为：

- StageResult：`failed`
- JSON：不存在
- HTML：存在，并包含“通过 (All Passed)”

修正要求：两个最终产物必须视为一组发布。任一最终发布失败时，不得留下本次运行生成的成功结论；可安全回滚本次新发布的文件，或把残留产物可靠地改为失败状态。不能删除或覆盖调用前已有的用户文件。

回归测试：包装真实 `os.replace`，允许 HTML 发布、仅让 JSON 发布失败；断言退出非零，且两个最终路径均不残留本次运行的成功结论。

### R2a-2（P2）：失败恢复会覆盖调用前已有的 JSON

位置：`run_status_stage` 中 `if target_json.exists() and target_json.is_file()` 后的直接 `open(..., "w")`。

该条件无法区分文件是本次生成的，还是运行前已经存在的。即使 HTML 目标是目录、JSON 从未成功发布，失败处理仍会直接覆盖旧 JSON；若写失败，还可能先把旧文件截断。

独立复现：预先写入 `env.json` 哨兵内容，再创建同名 `env.html` 目录触发 HTML 发布失败。程序返回 `failed`，但旧 JSON 哨兵内容被替换成新的失败报告。

修正要求：只清理或更新本次调用创建/替换的产物。失败报告本身也应先写临时文件，再原子替换；不得用直接 `open(..., "w")` 修改无法确认归属的旧文件。

回归测试：

1. 预写 JSON 哨兵并让 HTML 发布失败，断言旧 JSON 字节完全不变。
2. 模拟失败报告写入自身失败，断言旧 JSON 不会变为空文件或不完整 JSON。
